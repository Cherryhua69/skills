# Codex 会话命名整理

把目标会话命名为：

```text
真实项目简称 | 动作+核心对象
```

分隔符必须是半角竖线，左右各一个空格。项目简称建议 2～12 个字符，内容建议 4～14 个字符，完整标题通常不超过 28 个字符；英文仓库名等无法合理压缩时可以适度放宽。标题应短、可检索，并准确区分具体代码项目与本次工作的明确结果。

## 工作流程

1. 明确目标会话。当前会话可直接处理；批量整理或目标不明确时，先用 Codex 会话列表获取候选项及其 `threadId`、`hostId`、Codex 项目上下文和现有标题。
2. 分别识别每个会话实际操作的**具体代码项目**。同一 Codex 项目中的会话也必须逐个判断，不能共享套用一个项目名。
3. 从会话请求、结果与代码上下文提炼“动作+核心对象”，优先描述已经完成或正在推进的结果，而不是宽泛动作。
4. 生成标题并检查格式、项目身份和可检索性。用户要求直接整理时，用 Codex 的会话改名能力应用标题；用户只要求建议、方案或预览时不得改名。
5. 批量处理后简要列出“原标题 → 新标题”；只改当前会话时直接报告新标题即可。

## 识别具体项目

按以下证据综合判断，越靠前越优先：

1. 用户在会话中明确给出的产品、仓库、服务或模块名称。
2. Git 远端仓库名（例如 `git remote get-url origin`），去掉组织路径与 `.git` 后缀。
3. 项目清单或构建配置中的正式名称，例如 `package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、解决方案文件或服务编排配置。
4. README、部署配置、代码命名空间以及会话实际修改的文件所体现的项目身份。
5. 仓库根目录名只能作为低置信度线索，不能仅因它恰好等于当前工作路径就直接采用。

不要把下列内容当作具体项目名：

- Codex 项目/工作区名称；
- 当前工作路径的文件夹名；
- 局域网服务器的 IP、主机名或 SSH 别名；
- `backend`、`frontend`、`src`、`worktree` 等缺少业务身份的通用目录名。

同一 Codex 项目可能关联不同局域网服务器，而每台服务器又可能运行不同代码项目。必须结合该会话的 `hostId`、工作目录和仓库证据独立识别。服务器只用于定位证据，不能替代项目名。仅当不同服务器存在同名但并非同一项目、且标题会产生歧义时，才在项目字段中追加最短限定词，例如 `订单中心（测试服） | 修复退款回调`。

如果证据冲突，优先使用用户明确名称与仓库正式元数据；仍无法可靠判断时，先给出候选标题并说明缺少的唯一关键信息，不要编造项目名。

## 编写“内容”

- 默认使用“动作+核心对象”的简短动宾结构。动作优先从 `新增`、`修复`、`优化`、`重构`、`排查`、`设计`、`迁移`、`升级`、`审查`、`整理` 中选择；确有更准确的动词时可以使用，不机械套词表。
- 核心对象应包含可检索的业务名词，例如 `退款回调`、`登录性能`、`库存同步`，避免只写 `代码`、`问题`、`接口`、`功能`。
- 推荐标题示例：`支付中心 | 修复退款回调`、`用户中心 | 优化登录性能`、`管理后台 | 新增订单筛选`、`库存服务 | 排查同步失败`。
- 避免模糊标题：`支付中心 | 修改代码`、`用户中心 | 处理问题`、`管理后台 | 继续开发`、`库存服务 | 接口调整`。
- 保留能区分相邻会话的业务对象或故障现象，删除“帮我”“处理一下”“代码修改”“继续”等空泛词。
- 不罗列完整提示词、分支名、服务器名或实现步骤。
- 一个会话若包含多个动作，以主交付结果命名；如果确有两个同等重要且不可拆分的项目，可在项目字段使用 `项目A + 项目B`，但不要为了覆盖所有细节制造长标题。
- 用户明确指定标题时，保留其业务措辞，只修正格式或明显的项目身份错误。

## 检查清单

- 只有一个 ` | ` 分隔符；项目字段和内容字段都非空。
- 项目字段来自具体代码项目证据，而非 Codex 容器、路径或服务器。
- 内容字段采用明确、自然的“动作+核心对象”，足以和同项目下其他会话区分。
- 标题优先控制在 28 个字符以内；不得为满足长度而损害项目辨识或业务含义。
- 未执行用户没有要求的归档、删除、移动或分组操作。
